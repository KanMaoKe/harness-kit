# 可选模块设计草案

> 2026-10-26 状态：本草案中的模块生成能力已从 CLI 移除。设计、ADR、Issue、技术债与 Feature 文档应沿用项目已有体系，并在 `TASKS.md` 的「权威文档」中登记路径；Session 模块不再保留，当前交接使用 `STATE.json` 与 `resume`。下文保留为历史设计依据。

## 目标

harness-kit 先提供小而稳定的精简核心，同时预先设计面向复杂项目的可选治理模块。初始化默认只生成核心文件，不因为项目规模看起来大就自动加上所有模块。项目者可以逐项选择，也可以授权 AI 检查项目后提出模块组合；启用与生成结果应清楚可见、可调整。

它提供文件模板和维护工具，不替项目自动执行流程，也不假装模板会被 AI 自动加载。启用模块前，AI 可以查看项目已有的文档、入口和工作方式，说明需求依据、等效机制、重叠风险和将生成的路径。项目者可以自己选择；也可以明确要求 AI 按评估结果选择。没有选择或授权时不生成可选模块。已有文档承担同一职责时，优先沿用原文件并在 `TASKS.md` 中指向它，不创建第二份真相来源。

## 核心层

精简核心只负责建立基本项目上下文和跨会话接续：

| 文件 | 职责 |
|---|---|
| `PROJECT.md` | 项目目标、架构、稳定约定和验证入口 |
| `TASKS.md` | 项目协作约定、上下文选择和已有治理文档的入口 |
| `STATE.json` | 当前工作摘要：目标、状态、验收、验证、阻塞和下一步 |
| `HARNESS.json` | harness-kit 生成和档位元数据 |

精简核心是默认初始化结果，并默认作为本机 Git 本地排除对象。已有 `AGENTS.md`、项目 README 或任务系统时，入口只需链接到实际权威来源；需要项目入口时用 `--agents-md` 维护根 `AGENTS.md`，不在 harness 目录内生成第二份入口副本。

治理能力由多个独立模块组合而成。项目只启用实际需要的部分；例如复杂项目可以启用设计与 ADR、Bug、Feature 队列或技术债，但仍可不启用 Session 历史和日期日志。

## 可选模块

### 设计文档与 ADR

设计文档回答“这次要做什么、方案是什么、怎样验证”；ADR（Architecture Decision Record，架构决策记录）回答“为什么作出这项长期架构选择、考虑过什么替代方案、接受了哪些后果”。

二者面向不同记录对象：设计文档通常随功能从草案走向完成；ADR 在重要架构决定作出后保留为决策记录。不是每个功能都需要 ADR，也不是普通实现步骤都需要设计文档。若项目已有设计规范或 ADR 目录，只添加入口，不再生成并行体系。

建议模板字段：

- 设计文档：目标与非目标、范围、现状、方案、替代方案、风险、接口/迁移影响、分阶段计划、验收与验证。
- ADR：状态、背景、决定、考虑过的方案、理由、后果、相关文档。

### 交接 / Session 历史

交接记录回答“本次会话推进了什么，下一次如何接手”。建议内容包括已完成事项、实际验证证据、未决问题、阻塞和第一步下一步。

它与现有文件的边界：

| 记录 | 记录范围 |
|---|---|
| `STATE.json` | 最新的当前状态，作为恢复任务的简短入口 |
| `CHECKPOINTS.md` | 一个长期任务中的多个阶段节点、否决方案或搁置事项 |
| Session 交接 | 某次会话结束时的交接摘要，可链接到进度或设计记录 |
| 日期进度日志 | 按时间追加的已发生事实 |

默认由 `STATE.json` 承担当前任务交接：更新最新目标、状态、验证、阻塞和下一步即可，不另建 Session 记录。只有项目确实需要追溯每次会话的交接历史时，才启用 Session 历史模块，并按日期或任务采用条目式归档；它应链接到 `STATE.json` 和相关工作记录，而不是重复保存同一份当前状态。若项目已经用 `CHECKPOINTS.md` 或进度日志完成交接追溯，就不再启用 Session 历史。

### Bug 记录

Bug 记录缺陷自身的生命周期，不等同于任务状态或检查点。建议模板包括：标识与状态、现象、复现步骤、预期/实际结果、环境、影响、根因、修复、回归验证和相关变更。

`STATE.json` 可以表示“当前正在修这个 Bug”，但不应代替 Bug 记录。若项目已有 issue tracker，模板应改为记录链接和项目需要的补充信息，不复制 issue 全文。

启用本地 Bug 模块后固定采用条目式，并遵循下方统一的目录、索引、命名和元数据规范。Bug 不提供清单式模式；如果项目只需记一两条问题，可直接使用外部 Issue 或不启用该模块。

### Feature 队列与技术债

大型或多人项目可选启用 Feature 规划模块，默认关闭：

- Feature 注册表：列出项目功能项及其状态；当前队列：从注册表中标出近期要做的工作、优先级、负责人和下一步。两者可能各用一个索引文件。只有复杂 Feature 才额外建立设计和实施文档，不预先生成空文件。

单人小项目或只有一个当前任务时，`STATE.json` 通常足够；已有看板或项目管理工具时，harness 只需指向它们，不复制一套注册表和队列。

技术债默认采用一个 `TECH_DEBT.md` 清单。若条目数量、负责人或生命周期让单文件难以浏览和协作，可选择切换为条目式目录。已有外部债务清单时沿用原工具。

## 条目式规范

需要长期追踪、独立更新和定向读取的记录采用条目式。模块目录使用小写复数名，启用模块才创建对应目录；目录内的 `README.md` 说明模块用途、字段规则并提供索引。记录文件独立保存，索引只负责发现和跳转，避免重复维护状态等字段。

```text
.harness/
├── PROJECT.md
├── TASKS.md
├── STATE.json
├── bugs/                  # 启用 Bug 模块后创建
│   ├── README.md          # 用途、命名规则、记录索引
│   ├── BUG-0001-save-load.md
│   └── BUG-0002-inventory-stack.md
├── adrs/                  # 启用 ADR 模块后创建
│   ├── README.md
│   └── ADR-0001-save-format.md
└── debt/                  # 选择技术债条目式时创建
    ├── README.md
    └── DEBT-0001-legacy-api.md
```

条目式文件统一采用 `<TYPE>-<ID>-<slug>.md` 命名。类型和编号稳定，slug 简短描述主题；状态、严重度和负责人等可能变化的信息放在文件元数据中，不放进文件名或目录名。通用编号可以是 `BUG-0001`、`ADR-0001`、`DEBT-0001`；项目需要领域分类时，可在模块约定里自定义如 `BUG-UI-0001`，不强制所有项目建立领域代码表。

各类条目共享一组基础元数据，具体模板再补该类型字段：

```yaml
---
id: BUG-0001
type: bug
title: Save data is not restored
status: open
created: YYYY-MM-DD
updated: YYYY-MM-DD
owner: optional
related: []
---
```

`README.md` 的索引以 ID、标题和相对路径为主；易变状态以条目正文为准，避免索引与正文出现双重真相。模块条目可通过文件名、ID、标题及正文关键词搜索。工具未来可检查文件名与元数据 ID 是否一致、编号是否重复、必填字段是否齐全；不应仅凭文件数量自动切换存储模式。

不同模块选择适合自己的组织方式：

| 模块 | 默认组织方式 | 可选变化 |
|---|---|---|
| Bug | 条目式，固定 | 不提供清单式 |
| 技术债 | `TECH_DEBT.md` 清单式 | 项目主动选择后切换条目式 |
| 设计文档 / ADR | 每项文档独立文件，索引按需提供 | 项目自定义领域目录和 ID 规则 |
| Session 历史 | 默认不启用；启用后每个交接独立成文 | 按日期或任务命名 |
| Feature 注册表 / 当前队列 | 索引清单式，模块默认关闭 | 复杂 Feature 才有独立设计和实施文档 |

因此，“条目式”是通用存储规范，不代表每个模块都必须采用它；是否启用模块与模块采用何种组织方式是两个独立选择。

### 文档治理与工作流配置

可为有大量文档或多人协作的项目提供参考规则，例如文档命名、状态标签、信息冲突时的可信来源、复杂度门槛和完成定义。它们应是可选配置，不要把某个项目的 Feature ID、评审等级、分支命名或提交审批规则写成所有项目都必须遵守的硬标准。

工作流 Profile 和客户端适配暂不作为首批模块：在工具尚不能根据这些配置真正执行不同流程、且没有明确验证客户端兼容性前，配置容易被误解成自动生效的开关。

设计文档模板说明要记录哪些信息，不规定必须经过几级评审。普通项目可直接由项目者和 AI 使用模板推进；是否需要同伴评审、readiness 门禁或阶段 DoD，由项目自己的风险和团队流程决定。高风险改动可以在项目约定中增加评审要求，但不作为 harness-kit 默认规则。

## 与现有记忆文件的边界

完整档当前包含 `MEMORY.md`、`CHECKPOINTS.md`、`NARRATIVE.md` 和日期日志。可选模块应尽量复用这些已存在的记录，不默认堆叠新文件：

| 现有记录 | 可选模块的关系 |
|---|---|
| `MEMORY.md` | 存放简短、长期有效的经验；详细设计和正式架构决定应链接到设计文档或 ADR |
| `CHECKPOINTS.md` | 可以承担阶段交接；启用 Session 模块时明确选择替代还是互补，避免重复 |
| `NARRATIVE.md` | 记录少数重要演进脉络；不能替代有状态、有决定和后果字段的 ADR |
| 日期日志 | 按时间记录事实；不代替 Bug、Feature 或技术债的状态管理 |

如项目已经通过进度日志、Feature 注册表、ADR、Bug tracker 等记录同一类内容，应优先使用项目现有格式。重要结论可以在 `MEMORY.md` 中写一行摘要并链接原记录，而不是复制全文。

## 模块选择体验草案

模块选择可以有三种方式：项目者通过选项直接指定；AI 检查后给出建议，由项目者确认；或者项目者明确授权 AI 按检查结果选择。建议的交互顺序是“检查现状 → 展示建议/理由 → 确认模块组合 → 预览文件 → 写入”：

1. AI 阅读项目入口与已有文档，识别当前已有的 Bug、决策、交接、任务队列和技术债管理方式。
2. 对每个模块说明建议启用、暂不需要或已有等效机制，并附具体依据。
3. 项目者选择模块，或明确授权 AI 选择；可以拒绝、稍后决定或手动指定已有目录。
4. 工具预览将新增的路径和文件；确认后只补缺件，不覆盖已有内容。
5. 在 `TASKS.md` 或模块索引中写清楚权威文件位置及避免重复记录的规则。

AI 的评估不能只依据项目文件数量、代码量或技术栈。判断要基于实际协作需求、多人/多任务并行情况、历史记录体量、交接频率和现有工具缺口。未经项目者选择或明确授权，AI 只建议，不擅自增加文件。

模块选择结果应以简单、可读的清单记录在 `HARNESS.json` 或模块索引中，例如启用的模块 ID、模块目录和权威记录位置。工具据此报告当前配置；记录不存在的模块不影响核心使用。模块索引不复制模块正文，也不决定客户端如何加载文件。

## 建议实施顺序

1. 先把精简默认核心、模块选择记录、模板命名和“不与现有体系重复”的检查说明清楚。
2. 预先设计并提供可独立启用的设计文档/ADR、Bug、技术债和大型项目 Feature 规划模块；Session 历史作为有追溯需求时才启用的交接扩展。
3. 每个模块定义适用场景、是否采用条目式、命名和元数据规范、索引及与其他记录的边界；条目式遵守统一规范。
4. 验证初始化、模块选择预览、补齐、重复执行、模块配置变更和已有文件保护。
5. Profile、自动检测、自动注入或客户端适配另行评估，不能仅凭静态模板宣称已支持。
