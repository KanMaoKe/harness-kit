# harness-kit 产品评估与收敛建议

> 日期：2026-10-24。基于当前源码、模板、文档、29 项回归测试和本仓库自身的使用状态。本文记录判断，不表示相关改动已实现。

> 2026-10-25 更新：第一阶段和恢复闭环已实现。询问式 hook 与静音已移除；新增关键节点存档、本机项目登记、批量同步和项目身份/状态检查。本文其余部分保留当时的评估依据。

## 结论

harness-kit 最有价值的部分不是“自动记住 AI”，而是为已有项目提供一套**可预览、可保护、可恢复、可检查的本地协作上下文**。

当前主要问题不是功能不够，而是边界不够稳：

1. 询问是否初始化的 hook 与“用户主动接入”的产品方向相反，应删除。
2. 上下文是否被读取、是否及时更新，仍然只依赖 AI 遵守文字约定。
3. 元数据可以被轻易改成另一个项目，doctor 仍能报告健康。
4. 记忆、治理模板和宿主配置不断增加，但首次接入、恢复和状态可信性仍没有形成完整闭环。

下一阶段应该收敛，而不是继续扩张。目标是：**初始化有明确入口，现有内容不被误改，任务恢复不靠重新调研，状态问题能被检查出来。**

## 当前做得好的部分

- 标准库 CLI，直接运行，不依赖模型、API Key 或特定宿主。
- 初始化和同步保留已有正文，`--force` 的范围清楚。
- 首次 dry-run 与正式执行共用计划，适合已有项目安全接入。
- `.harness/` 默认本地私有，避免调研、任务摘要和私人上下文进入产品仓库。
- `STATE.json` 把稳定规则与当前任务分开，符合单一事实来源。
- `AGENTS.md` 采用受管片段，保留片段外的用户规则。
- 不自动暂存、提交、推送或覆盖项目文档。

这些应成为产品主线，不应为了自动记忆而重写。

## 主要问题与判断

### 1. 询问式 SessionStart hook 应删除

它只关心“项目是否初始化”，已有 harness 时反而退出，不能解决恢复问题；为了它还维护静音名单、会话去重、宿主配置、hook 安装与卸载。默认又关闭，用户主动安装后仍可能什么都看不到。

**决定建议**：删除 `hook_session_start.py`、`mute.py`、静音状态、提示开关和相关推荐；不要把它改成更复杂的询问流程。

`AGENTS.md` 是可移植入口，`resume --json` 是机器可读入口。某个宿主确实需要 SessionStart 恢复适配时，应作为后续独立功能设计和验证，不与初始化询问捆绑。

### 2. “给了路径但 AI 重新调研”不是缺记忆，而是缺接入和状态治理

产品只能保证文件存在、入口可读，不能保证每个 AI 自动发现或执行规则。完整记忆不能解决这个问题，反而会增加读取成本和相互矛盾的内容。

**决定建议**：不开发自动总结全部对话、自动写长期记忆或全量上下文注入。保留 `STATE.json` 为唯一当前任务摘要，优先提供简短恢复信息。

### 3. 当前 doctor 检查结构，不检查上下文是否可信

本仓库自己的 `HARNESS.json` 已被改成 `project: AIMV Research`，并启用了 Bugs、Design、ADR、Feature 和技术债；`PROJECT.md` 却仍是 harness-kit，且明确不启用这些模块。doctor 当前仍报告无问题、无警告。

这不是要求工具禁止人工编辑，而是说明“文件齐全”被误当成了“上下文有效”。

**决定建议**：增加上下文一致性检查，而不是增加自动写入：

- `HARNESS.json` 的项目标识、类型与 `PROJECT.md` 是否一致。
- `STATE.json` 是否描述一个已经结束的旧任务，是否给出真实下一步。
- `AGENTS.md` 是否存在、受管标记是否完整，是否指向实际 harness 目录。
- 是否存在已删除产物、重复备份或多个权威来源。
- 已启用模块是否确实在项目约定中声明使用，不能只看文件存在。

报告应区分“结构完整”“配置一致”“状态可能过时”，不要合成一个质量分数。

### 4. Git 本地私有与入口共享需要拆开

`.harness/` 本地私有的方向正确，但会让其他机器或只读取 Git 的 AI 看不到上下文。根 `AGENTS.md` 是入口，不属于 harness 私有状态，不能只靠本地未跟踪文件提供接入。

**决定建议**：明确入口文件的共享策略。需要兼容的 AI 自动发现时，根 `AGENTS.md` 应该能随项目共享；其中的正文只指向 `.harness/` 的权威文件，不包含私人任务内容。其他机器仍需本地初始化自己的 harness，不能把本地状态当成共享内容。

### 5. 安装与生命周期过重

普通 CLI 不需要安装，却又提供复制安装、宿主配置、技能安装、hook 注册、卸载清单等多条路径。卸载使用源码目录的 hook 脚本，复制安装后的卸载与记录失效场景也没有完整覆盖。

**决定建议**：先保留“直接运行”和“复制工具/安装技能”两条路径。删除询问式 hook 后，再简化卸载和宿主配置，避免在旧机制上继续打补丁。

### 6. 记忆与治理扩展先冻结

compact 已足以承载当前项目协作。comprehensive 的记忆、叙事、检查点、日期日志，加上六种治理模块，让维护范围远超当前主路径的实际验证能力。

**决定建议**：现有扩展暂时保留读取和文件保护，不继续新增模块、模板或自动行为。主路径稳定后，再根据真实使用证据决定保留、简化还是移出核心。不要主动给项目启用全部模块。

### 7. 模板需要减少“生成很多待填空项”的冲动

`PROJECT.md` 和 `TASKS.md` 同时承担背景、规则、流程和通用工程原则，容易让 AI 把模板文字当成项目事实。技能模板中的通用认知分类也与主产品价值关系较弱。

**决定建议**：模板优先记录“这个项目特有的事实和规则”，通用工程常识不必在每个项目复制。模板瘦身应在主路径稳定后单独进行，避免和入口、状态治理同时改变太多契约。

## 建议实施顺序

### 第一阶段：删掉错误方向，建立可信基线

1. 删除询问式 SessionStart hook、静音和相关配置。
2. 明确 `AGENTS.md` 与 `.harness/` 的共享边界。
3. 扩展 doctor，检查项目身份、入口和状态一致性。
4. 修复安装/卸载中仍然成立的错误路径与错误成功报告。
5. 让测试在受限环境和不同临时目录策略下可运行；不以环境错误代替通过结果。

### 第二阶段：形成可验证的恢复闭环

1. 把 `resume` 的摘要生成提取为可复用函数，CLI 和可选宿主适配共用。
2. 提供“当前目标、验收、验证、阻塞、下一步”的简短恢复信息，不注入完整历史。
3. 给 `STATE.json` 增加可核查的新鲜度或任务边界检查；只报告问题，不自动重写用户状态。
4. 增加一个完整填写的小项目示例，验证初始化、一次任务、状态更新、doctor 和新会话恢复。

### 第三阶段：根据证据做减法

1. 检查 comprehensive 和治理模块是否有人实际使用，未验证的不继续扩张。
2. 简化模板中的通用规则和重复说明。
3. 再评估是否保留 `status` 批量扫描；如果没有多项目使用场景，不应优先投入。

## 明确不做

- 不做“询问项目是否需要 harness”的交互。
- 不承诺每个 AI 自动读取、自动记忆或自动完成验收。
- 不自动总结对话、写长期记忆或重写 `STATE.json`。
- 不自动运行任意项目测试来伪造验证记录。
- 不新增更多记忆类型、治理模块、宿主配置或工作流档位。
- 不把本地 `.harness/` 状态默认推入 Git。
- 不为了实现自动恢复而引入模型调用、向量库或任务编排运行时。

## 验收方向

下一阶段完成后，至少应能验证：

1. 新项目通过 dry-run 和 init 接入，已有正文不被覆盖。
2. 兼容客户端能通过入口找到权威文件；其他客户端可使用 `resume --json`。
3. 项目名称被改错、状态过时、入口标记损坏时，doctor 不再报告完全健康。
4. 新会话能恢复同一个当前任务，而不是重新生成一份项目调研。
5. 测试报告只声称实际通过的检查，环境阻塞单独列出。
