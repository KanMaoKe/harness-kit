# 设计说明

harness-kit 将跨会话协作需要的信息放进普通项目文件，以命令行维护结构。它同时约束 Agent 的工作方式和项目上下文，默认生成精简核心；通用记忆与技能指南可按项目需要显式启用。项目已有的设计、Issue、ADR 等文档只登记权威路径，不复制正文。它们都是可编辑文件约定与维护工具，不构成自动上下文运行时。

## 文件分层

| 层 | 文件 | 内容 |
|---|---|---|
| 项目规则 | `PROJECT.md` | 目标、架构、命名、开发与验证约定 |
| Agent 工作准则 | `TASKS.md` | 澄清、范围控制、修改边界、验证和交接规则 |
| 当前任务 | `STATE.json` | 目标、状态、验收、验证、阻塞与下一步 |
| 记忆 | `memory/` | 长期事实、阶段决策、转折与日志 |
| 技能 | `skills/` | 可重复执行的流程及验收方式 |
| 权威文档 | `TASKS.md` 中的路径 | 指向项目已有的设计、ADR、Issue、技术债或 Feature 文档 |
| 元数据 | `HARNESS.json` | 项目类型、工具版本与生成记录 |

这些文件按用途分开，便于单独修改和按需读取。生成后仍需要结合项目补全；空模板只能提供结构。

根 `AGENTS.md` 不是 harness 目录内的规则副本，而是可选的项目入口。只有显式使用 `--agents-md` 时才创建或更新其中由 harness-kit 管理的标记片段；`.harness/` 内不再生成第二份入口副本。

设计、ADR、Issue、技术债与 Feature 管理属于项目已有文档体系。harness-kit 不再生成这些模块；`TASKS.md` 只登记实际权威路径。已有载体承担相同职责时，应沿用并链接原记录。

## 上下文选择

先确认当前目标，再读取相关文件。稳定规则通常比历史日志优先，近期决策通常比完整历史更适合恢复工作。需要查证时再沿记录中的路径读取原始依据。

任务未知时读取项目摘要并澄清目标，避免因关键词未命中而丢弃工作上下文。工具选择与文件读取规则由 AI 和宿主执行，脚手架不控制模型调用；TASKS.md 的工作准则和上下文选择是协作约定，不是自动注入规则。

## Agent 工作契约

通用工作方式只在 `TASKS.md` 维护一处，`PROJECT.md` 不再重复“最小改动、先定位、遵守范围”等通用条目。当前契约覆盖五组行为：

- 先澄清假设、歧义和取舍，再定位和实现。
- 只解决当前问题，不预造功能、抽象和扩展点。
- 把任务转成可验证目标，真实运行检查，未验证不标记完成。
- 项目事实、工作规则、当前任务和历史记录保持单一事实来源。
- 在关键节点存档，换会话或客户端时恢复同一个任务。

`TASKS.md` 的 Agent 准则使用受管标记。`sync --refresh-agent-rules` 只替换标记内正文，保留其他项目规则；标记缺失、重复或顺序错误时拒绝写入。

## 记忆维护

- 项目事实写入 `PROJECT.md`，当前任务写入 `STATE.json`。
- 历史档案只在确有追溯价值时写入，检查点记录关键决策、否决理由与下一步。
- 项目已有设计、ADR、日志或知识库时，继续沿用并在 `TASKS.md` 中登记路径。
- 客户端记忆负责个人偏好与跨项目习惯，项目文件负责可检查、可共享的项目上下文。

完整的四层边界、写入时机与外部检索接入条件见 [记忆设计](记忆设计.md)。harness-kit 不监听完整对话，也不重复生成另一套自动记忆；未在关键节点存档的对话细节无法凭空恢复。

## 技能组织

用明确的名称和触发说明描述技能，命中任务后再读取正文与参考资料。技能可以覆盖完整任务，也可以组合小步骤；认知原语只是可选拆分方式。

步骤应说明输入、产出与验收，不要求展示内部思考过程。保留可核查的决策依据、工具结果和验证证据即可。

## 文件保护

初始化默认补缺件、保留已有正文。显式使用 `--force` 才覆盖 `PROJECT.md`，已有任务规则、技能与记忆正文仍保留。同步只补缺件并更新元数据，不自动迁移已有正文。

项目文件固定使用 `.harness/`，运行状态默认使用 `~/.harness-kit/`。代码、状态和宿主目录分别管理；旧目录中的项目内容需要由 AI 按新结构重读和重写，不保留自动兼容。

## 生成计划与 Git 归属

初始化先生成内存中的完整计划，`--dry-run` 只输出该计划，正式执行写入同一计划。计划包含目录、文件、跳过项、入口变化和 Git 排除变化，避免预览与实际行为分叉。

`.harness/` 默认作为本机 AI 协作上下文，不随项目进入 Git。目标位于 Git 工作副本内时，工具在 `.git/info/exclude` 中维护 `<harness目录>/` 规则；根 `.gitignore` 不变，也不自动执行 Git 暂存、提交或推送。显式使用 `--share-harness` 时记录共享意图并移除本工具添加的本地规则。`HARNESS.json` 的 `git_visibility` 字段记录意图，实际忽略状态由 Git 与体检核对。

不支持普通 Git 目录、worktree 或 Git 命令不可用时，项目文件仍可生成，只跳过本地忽略。体检会把声明与可检测到的实际状态进行比较。

## 本机登记与一致性

初始化成功后在本机 `projects.json` 登记路径，`sync --registered` 支持预览与批量补缺。登记不包含项目正文；dry-run 不写登记。项目身份与 `PROJECT.md` 不一致时，批量同步跳过该项目，其他项目继续。

`doctor` 区分结构完整和上下文一致：项目标题与元数据冲突是问题，状态长期未更新、缺少验证或 Git 归属不一致是警告或提示。检查不会自动改写用户状态。

## 接入与提示

命令行无需宿主即可直接从源码运行。只有安装技能时，才显式指定 `--skill-dir` 或 `--host-config-dir`；安装器写入实际源码路径，不复制代码、不写安装清单、不注册 hook。

项目指令入口支持因客户端而异，兼容性需要实际验证。可选 `--agents-md` 维护根 `AGENTS.md` 标记片段；未指定时不创建项目入口。其他客户端可使用 `resume --json`。生成文件不代表客户端已经实际加载。

## 验证边界

体检检查结构与部分文本特征，不能评估项目设计质量或证明任务完成。实际改动仍需运行项目适用的测试，并记录验证结果。

当前限制、公开规范对照与改进优先级见 [项目设计检查](项目设计检查.md)。
