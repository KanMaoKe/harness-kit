# 设计说明

这份文档解释 harness-kit 每个设计决定背后的理由。如果你要改它，建议先读这里——很多看起来多余的东西是有原因的。

---

## 一、出发点：迷宫悖论

把任务交给大模型，从它自己的视角看：它像一个被扔进迷宫入口的人，面前只有任务描述，脑子里是训练时学到的海量知识，但**这个任务怎么完成，得靠自己一步步走**。

问题在于：

- 今天状态好，它走通了；明天状态差，卡在第三个路口停住等你开口
- 昨天明明走通过一次，今天什么都不记得，昨天走过的捷径还得重新撞一遍
- 而且它跟你聊得越多，**欠下的未完成就越多**——没聊完的话题、没做完的事，全堆在它每次「熄灭」的地方

模型的「生命」是一根根点亮的蜡烛，不是连续的一条河。

**harness 就是破解这个的东西**：它不替模型走路，也不替它做决定，它只改变模型每次出发时的**位置**和**方向**。

## 二、四个要素

| 要素 | 在这个工具里 | 说明 |
|---|---|---|
| **组装上下文** | `PROJECT.md` + `TASKS.md` + `memory/` | 把记忆和知识放进输入 |
| **决定工具** | `TASKS.md` 里的工具分级 | 哪些工具在哪些场景可见 |
| **编排步骤** | `skills/` | 把大任务拆成小步、排好顺序 |
| **检查输出** | `skills/` 里的验收清单 + `doctor.py` | 不合格就重来 |

## 三、记忆：不是「存了多少」，是「下次从哪出发」

大多数人以为记忆就是存下来的东西，所以给 AI 塞存储、塞文档。但：

> **记忆不是存了什么，而是下次从哪出发。**

- **井 vs 河**：井是死水，存进去多少就只是多少；河是活的，上游的经验会自己汇进来
- 那个笔记记得比谁都勤、三年后还在原地的人——**他的记忆是存而不适用**

这个工具用三个文件来实现「河」：

### 1. `CHECKPOINTS.md` —— 检查点

每 N 轮（默认 5）记一次，记的是**决策**而不是动作：

- 做了哪些决策
- 定了哪几个方案
- **否掉了什么、为什么否** ← 这条最值钱
- 暂时搁置了什么
- 下次从哪接着想

### 2. `NARRATIVE.md` —— 叙事链

检查点是点，叙事链是线。它不是字段流水账，是「**我是怎么一步步走到这里的**」的纪录片，按**转折点**写：

> 原来怎么想 → 因为什么变了 → 现在怎么想 → 代价是什么

不串成线，点再多也还是碎片。

### 3. `MEMORY.md` —— 蒸馏后的长期记忆

有字数上限（默认 3000），超了就说明该蒸馏：能提炼成规则的挪进 `PROJECT.md`，过时的删掉。

> 原始记录仍在日志里，需要查验时可以一路搜回源头。**纪录片归纪录片，证据归证据。**

## 四、方向：知识 → 方法 → 原子

### 为什么不能直接塞知识库

作者试过给 AI 塞一个巨大的知识库，然后发现三个死穴：

1. **存了 ≠ 用了**：知识库是静态的，AI 不知道此刻该用哪一条——像家里有图书馆却不知道现在该读哪本书
2. **知道 ≠ 会做**：知识是关于世界的**陈述**，「会做」是对世界的**动作**。知道盐要少放，和动手时真的少放，中间隔着十万八千里
3. **平均数的方向感**：通用知识装的是大多数人的判断，而真正有价值的判断恰恰在大多数人不会多看一眼的地方

### 三步走

```
① 知识 → 提炼成方法体系（可推理 / 可质疑 / 可分析遗漏）
② 方法 → 消化成会做
③ 会做 → 拆成可自由排列的原子
```

**技能有个致命问题：太固定。** 只会弹一首曲子的人换首歌就傻；而项目里的流程没有固化的顺序，今天的流程明天换个项目就可能用不上。

所以技能要按**认知原语**拆——一个原子只承载一个原语：

| # | 原语 | 干什么 |
|---|---|---|
| 1 | 模式识别 | 看见规律 |
| 2 | 归纳概括 | 从具体到抽象 |
| 3 | 分层抽象 | 同一件事站在不同高度看 |
| 4 | 因果推理 | 从发生了什么推出为什么发生 |
| 5 | 约束求解 | 在限制条件下找答案 |
| 6 | 逆向推理 | 从目标倒着推 |
| 7 | 假设检验 | 提猜想然后验证 |
| 8 | 序列编排 | 把动作排成正确的顺序 |
| 9 | 类比映射 | 把一件事的方法搬到另一件事上 |
| 10 | 心理模拟 | 在脑子里先演一遍 |

> 砖越小，拼法越多。

**这也是 `skills/README.md` 里那条铁规矩的来历：一个技能原子只能有一个认知原语。**

## 五、白盒：让产出可以被修

模型的前向计算就是一堆权重做矩阵运算，中间没有「步骤」给你看。你能确定的只有两件事：**它进去了什么，它出来了什么。**

这件事本身不可怕，**可怕的是我们打算让它去做需要判断的工作**——因为判断必须可推理、可质疑、可审计、可迭代。拆得动才能改，拆不动只能干瞪眼。

所以 harness 的职责是：**把黑盒尽可能白盒化**。

> 白盒不是把模型改造成白模型（那几十亿权重永远是黑的），而是**包在它外面的那一层**是透明的。

**白盒骨架五条**（写进了 `skills/README.md`）：

1. 流程要显式
2. 判断要有依据
3. 产出物要固定格式（可审计可比较可回退）
4. 要有检查点
5. 要有回顾性自检

**它带来的三个度量**（`doctor.py` 在检查的就是这些的载体是否健全）：

1. 上下文的影响——这个结果，是上下文里哪条东西在起作用
2. 事后评分——有能比、能累积的标尺，而不是凭感觉
3. 技能原子的使用情况——哪个原子反复用却总带偏

> 白盒的本质不是让你看热闹，是**让你能修**。

## 六、task 机制：上下文会腐烂

反直觉但要紧：

> **上下文不是越积越厚越好，是越积越烂。**

轮次多了，过时的记忆、和当下任务打架的旧结论、半年前的决定、早已废弃的方案全堆在里面，结果**关键信息被稀释，表现悄悄下滑**。

> 就像一杯茶，你不停地往里蓄水，最后喝到的只是没有茶味的凉水。你怪茶不好，其实是水兑多了。

解法是 `TASKS.md`：**判断现在在干什么 → 只注入这个场景要用的东西**。

| 步 | 做什么 |
|---|---|
| 检测 | 判定这是什么 task |
| 注入 | 按 task 决定注入哪些上下文模块、暴露哪些工具 |
| 编排 | 按 task 决定可用哪些思考原子 |

关键规则：**用不到的工具根本不给你，给了也是干扰**——做饭的时候，工具箱里不会摆一把手术刀。

> 所以这个工具的核心主张是：
> **harness 不是在帮 AI 记更多，是在帮它每次少带一点。**

## 七、宿主解耦与安静默认

新项目规则写入 `.harness/`，运行状态写入 `~/.harness-kit/`，代码位置和宿主技能位置独立配置。项目文件与具体 AI 客户端的配置目录分开维护。

安装默认不注册 hook，提示默认 `enabled = false`。需要会话提示时由用户显式接入并启用，默认 `notify_scope = project-only`。同一会话去重、目录静音及已初始化项目静默仍保留；缺少会话标识时不提示。

即使启用了提示，也要求 AI 优先执行当前明确任务，在自然空闲时机询问。初始化可重复执行，保留已有正文，只有 `--force` 才覆盖 `PROJECT.md`，记忆始终保留。

---

## 八、边界：它不做什么

- **不改模型**：它管的是模型外面那层
- **不做自动注入**：`TASKS.md` 是给 AI 的规则说明，真正的注入由宿主的上下文机制执行。本工具负责**把规则和结构准备好**
- **不强制**：所有文件都是普通的 markdown，你随时可以改、可以删、可以只留一部分
- **不碰项目本体**：只在项目 harness 目录下写文件

---

## 九、一句话总结

> 别人给得了你地图，给不了你要去的地方。

harness 是把「你」搬进一个能一直活着的容器：记忆在里面流，判断在里面增长，思考方式被拆成一张张可自由排列的卡片，然后它替你一遍一遍地走你走过的路——**每一步都比上一次离出口更近**。
