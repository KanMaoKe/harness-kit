## 一、总体结构对照

视频说 harness 管四类事，本工具的对应：

| 视频原文（harness 管四类事） | 本工具落地 | 具体文件 |
|---|---|---|
| ① **组装上下文**：把记忆和知识放进输入 | 宪法 + 任务规则 + 记忆层 | `PROJECT.md` `TASKS.md` `memory/` |
| ② **决定工具**：让模型能调用外部能力 | 工具分级规则 | `TASKS.md` 第四节 |
| ③ **编排步骤**：把大任务拆成小步、排好顺序 | 技能层 + 执行表 | `skills/` `skills/README.md` 第六节 |
| ④ **检查输出**：不合格就重来 | 验收清单 + 体检工具 | `skills/README.md` 第七节 + `kit/doctor.py` |

视频的核心判断：**「harness 不替 agent 走路，也不替它做决定，它改变 agent 每次出发时的位置和方向。」**
→ 本工具不生成内容、不替你做判断，只准备**位置（记忆）**和**方向（宪法+技能）**的基础设施。

## 三、覆盖率小结

| 类别 | 条数 | 状态 |
|---|---|---|
| **完全落地**（文件中可直接找到） | 24 | ✅ |
| **原理落地、执行依赖宿主** | 3 | ⚠️ |
| **未落地** | 0 | — |

三条「原理落地、执行依赖宿主」的是：
1. 双轨检索（BM25 + 向量）
2. 预注入
3. 间隙注入

**为什么依赖宿主**：这三条都是**运行时行为**，需要宿主在每次调用模型时介入。
本工具是文件层的脚手架，只负责把规则写成 AI 读得懂、守得住的文本——
真正的执行者是 WorkBuddy / CodeBuddy 的上下文注入机制。

这不是偷懒，是**能力边界**：写脚手架的工具不该假装自己能控制推理时的上下文。

## 四、本工具**不**做的事（边界）

对照视频，明确划清边界，避免误解：

| 视频里作者做的事 | 本工具是否做 | 原因 |
|---|---|---|
| 自己写 harness（Nebula），控制每轮注入什么 | ❌ 不做 | 那是宿主（WorkBuddy）的职责 |
| 接 BM25 + 向量自建检索 | ❌ 不做 | 同上 |
| 写设计骨架（行为净值公式、归因引导等） | ❌ 不做 | 那是**领域内容**，属于你的 `PROJECT.md` |
| 造「设计 agent」并写它的 prompt | ❌ 不做 | 同上 |
| **准备项目的宪法、任务规则、记忆结构、技能规范** | ✅ **做** | 这是脚手架该干的 |
| **在会话开场询问是否要建** | ✅ **做** | 通过 SessionStart hook |
| **体检记忆是否腐烂、结构是否健全** | ✅ **做** | `kit/doctor.py` |

一句话：**本工具造容器，容器里装什么由你决定。**
