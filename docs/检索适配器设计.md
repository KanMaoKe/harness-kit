# 检索适配器设计

> 状态：设计建议，尚未实现。2026-10-31 基于当前仓库、资料型项目样例和公开一手资料编写。

## 结论

harness-kit 需要为资料型项目提供**可选的检索接入**，但不应把向量数据库、嵌入模型或完整 RAG 框架塞进核心。

这里先区分三个词：

- **知识库**：项目自己维护的文档集合，例如 `docs/`、ADR、接口说明、运维记录。它是事实来源。
- **检索索引**：从这些文档生成的查找入口，是派生数据，可以删除和重建，不是另一份事实来源。
- **RAG**：检索增强生成。检索到资料后交给模型辅助回答；本设计只负责“找资料”，不负责让模型自动写作。

产品负责统一调用和结果契约，具体检索实现是独立、可选的适配器。普通项目继续使用 `rg` 或宿主搜索，不增加依赖。

## PSB

- **问题**：资料型项目可能有几十到几百份文档。项目分层能帮助 Agent 找入口，但不能回答“哪些文档与当前任务相关”。逐份阅读浪费上下文，也容易漏掉跨文档关系。
- **方案**：提供显式启用的检索适配器，先支持可解释的关键词/子串检索，再按真实失败案例增加语义后端。
- **收益**：Agent 能快速定位应读的资料，普通项目不被迫安装模型，索引和原文的权责也保持清晰。

## 不应混淆的产品边界

| 项目 | 负责什么 | 不负责什么 |
|---|---|---|
| harness-kit 核心 | 项目上下文、Agent 工作准则、任务状态、检索调用约定 | 不内建嵌入模型、向量运行时或自动记忆抽取 |
| 检索适配器 | 扫描指定文档、生成索引、返回匹配位置 | 不改写权威文档，不替 Agent 判断内容是否正确 |
| Agent / 客户端 | 根据任务检索、打开原文、综合判断并验证 | 不因检索命中就宣称结论已被证明 |

## 使用方式

建议未来提供一个与现有 CLI 风格一致的可选命令：

```bash
python kit/search.py --path "<项目>" --query "后台上传权限" --limit 5
```

`search.py` 只负责读取项目登记和适配器配置、执行显式查询、输出结构化结果。首次检索或文档变化后可显式更新索引；不在每次聊天或 `resume` 时后台重建。

`TASKS.md` 的「权威文档」登记文档清单入口及可选检索方式；`STATE.json` 只保存当前任务摘要，不存检索结果副本。`resume` 仍然只返回当前任务和优先读取文件，不自动注入检索内容。

## 返回契约

建议每个结果包含：

```json
{
  "ok": true,
  "query": "后台上传权限",
  "adapter": "keyword",
  "index_status": "fresh",
  "results": [
    {
      "path": "docs/03-backend/security.md",
      "start_line": 42,
      "end_line": 51,
      "heading": "上传校验",
      "text": "与查询相关的原文短片段",
      "match": "literal",
      "source_sha256": "..."
    }
  ]
}
```

原则：

1. **路径和行号是主要结果**，文本只用于帮助 Agent 判断是否值得打开。
2. 每个结果能定位到原文，不能只有无法核查的模型摘要。
3. 结果数量默认少而精；不把整个知识库或前几十段全部塞进上下文。
4. 返回索引状态；文件变化后必须标记过期，不能把旧片段伪装成当前事实。
5. 检索无命中不自动补写答案，应返回空结果或建议扩大关键词。

这与 Anthropic 的“just in time”上下文策略一致：保留文件路径、查询和链接等轻量标识，需要时再用工具加载原文。目标是让 Agent 选择最小必要上下文，而不是预先注入全部相关资料。

## 第一版：关键词与子串检索

第一版优先支持 Markdown、纯文本和项目已有的结构化文本导出，按标题边界和自然段落切块。先服务真实需求：模块名、接口名、错误码、配置项、已知术语和跨文档查找。

候选实现是独立进程中的 SQLite FTS5 或等价的本地索引。SQLite FTS5 官方支持 `bm25()` 排序、外部内容表和片段辅助函数；本机已验证 Python 3.47.2 自带 FTS5 可用。

但必须明确一个限制：本机验证中，默认 `unicode61` 分词无法直接以“上传”命中“用户上传权限校验”，`trigram` 也不能覆盖所有短中文查询。因此不能把 SQLite 默认配置当作中文检索的完整答案。

实施时需要：

- 对中文/中英文混合文本使用经过测试的本地分词或子串索引。
- 保留英文和数字的词检索，处理连字符、下划线和大小写。
- 设计中文短查询、长术语和混合查询的验收样例。
- 对无法可靠覆盖的文本明确降级为文件搜索，不虚报“已支持所有语言”。

如果引入中文分词库，它应属于检索适配器的可选依赖，而不是 harness-kit 核心运行时依赖。

## 语义后端：按需增加

当关键词检索对真实任务反复出现以下失败时，再增加语义后端：

- 用户说法与文档术语不同，但意思相近。
- 需要按概念找文档，不知道具体函数名或配置项。
- 同一主题分散在多个文档，关键词只能命中局部。

届时可选择本地向量库或外部检索服务。LanceDB 官方支持向量、全文和 SQL 检索，也提供嵌入式部署；但向量生成仍需要嵌入模型和额外依赖，不能因为数据库可本地运行就声称“零配置 RAG”。

语义后端不是第一版的必选项，也不需要 LlamaIndex 这样的完整框架。若未来确需复杂文档解析或现成模型集成，再单独评估框架成本。

## 暂不采用记忆运行时

Mem0、Letta 等系统解决的是记忆抽取、会话状态和个性化记忆运行，不等同于项目文档检索。Mem0 官方也明确涉及 LLM、嵌入模型以及多信号检索。

它们不是本设计的默认底座。只有当需求从“查项目文档”扩展到“从大量对话中抽取并维护长期记忆”时，才单独评估，不能用它们替代项目权威文档。

## 索引维护

- 索引是派生数据，默认放本机私有运行目录，不进入产品仓库。
- 记录源文件路径、大小、修改时间和内容哈希；查询时提示索引是否过期。
- 删除或移动文档后，索引同步清除对应条目。
- 更新必须可预览、可重建；不要求保留旧索引作为迁移包袱。
- 只索引明确登记的文档目录，不默认读取整个用户目录或私人配置。

## 非目标

- 不自动总结所有文档或生成第二份“知识库事实”。
- 不自动把检索结果写进长期记忆或 `STATE.json`。
- 不在 `resume`、初始化或每次对话中自动执行检索。
- 不强制嵌入模型、云端 API、LLM 重排、知识图谱或 Agent 编排。
- 不在第一版支持 PDF/OCR、音视频转录、全格式文档解析或 MCP 服务。
- 不承诺检索到就等于事实正确；代码、测试和权威文档仍是验证依据。

## 验收设计

在真实资料型项目中准备一组固定问题，覆盖：

1. 已知模块名、接口名和错误码的精确定位。
2. 中文短词、中文长术语和中英文混合查询。
3. 不知道具体术语时的相关文档查找。
4. 跨模块问题需要打开哪些文档。
5. 文档修改、删除和移动后，旧索引是否被正确标记或清除。

每个问题记录：预期命中文档、实际命中、原文行号是否可定位、是否需要语义检索、失败原因。先做关键词基线，再决定语义后端是否有实际收益。

## 建议实施顺序

1. 选定一个真实资料型项目，建立 10–20 个检索问题和基线。
2. 实现只读的关键词/子串检索适配器，验证中文召回和路径定位。
3. 接入 `search` 命令与 JSON 输出，保持 `resume` 不变。
4. 在真实任务中比较“无索引 / 关键词检索 / 可选语义检索”的命中与上下文成本。
5. 只有证据表明关键词不足时，才实现语义后端。

本设计尚未实现，不代表当前已经具备知识库、RAG 或向量检索能力。
