# 参考项目评估：skills-skills 与 superpowers

> 评估日期：2026-10-28。对象为本地参考目录中的 `skills-skills-v0.60.0` 与 `superpowers-main`。本文记录设计判断，不代表已经复制或安装参考项目。
>
> 2026-10-28 更新：已按本文建议将“先读再问、根因排错、本次证据”合并进 `TASKS.md` 的受管 Agent 工作准则；未新增 hook、技能包或运行时。

## 结论

这两份参考项目都有价值，但解决的问题不同：

- `skills-skills` 是大型内容技能库，重点是技能目录、安装、校验和发布。
- `superpowers` 是编码 Agent 的开发方法论，重点是澄清需求、计划、排错、验证和交付。

对 harness-kit 更有参考价值的是 `superpowers`。它验证了产品不应只提供项目上下文，还应约束 Agent 的工作方式。

但不建议直接复制任何一份参考项目。harness-kit 应继续保持窄边界：**Agent 工作准则、项目事实和任务恢复**。可以吸收具体原则，不引入完整工作流运行时、技能市场或自动注入 hook。

## 评估范围

已只读查看：

- 两份项目的 README、Agent 规则和目录结构。
- `skills-skills` 的技能分组、安装说明、设计决策、应用测试和校验脚本。
- `superpowers` 的核心技能、计划流程、系统排错、TDD、完成前验证、插件清单和 SessionStart hook。

两份参考目录都不是 Git 工作副本，因此本文依据当前文件内容评估，不判断它们的历史版本或发布稳定性。

## 项目一：skills-skills

### 它是什么

一个面向 Scenario 内容生成与 DCC 工具的 Agent Skills 目录，约有 82 个技能。它通过 `skills.sh` / `npx skills` 安装，技能覆盖图片、视频、3D、游戏引擎和团队管理。

### 做得好的地方

1. **技能有清楚的分组和用途**

   每个技能有名称、描述、适用任务和安装入口。用户既能安装全部核心技能，也能按角色或目标选择子集。

2. **不把“写了技能”当成“技能有效”**

   它有格式校验、脚本测试和应用测试。应用测试会让一个没有对话历史的新 Agent 只读技能正文和任务，然后检查它是否能给出正确执行计划。

3. **规则有决策记录**

   `docs/decisions.md` 记录规则背后的原因和证据。后来的人可以判断某项规则为什么存在，而不是只看到一句命令。

4. **技能按责任拆小**

   技能不是一篇巨型说明，而是有明确触发范围、输入、输出和验收。需要更多上下文时再链接参考文件。

5. **发布和更新路径清楚**

   有安装、更新、版本、变更记录和 CI 校验。用户可以判断自己安装了什么，以及如何更新。

### 不适合 harness-kit 的地方

1. **它是领域内容库，不是项目脚手架**

   大多数价值来自 Scenario MCP、模型选择、素材生成和 DCC 操作，与项目上下文和任务恢复不是同一层。

2. **技能数量和维护面过大**

   82 个技能需要持续验证模型、工具、脚本和平台行为。harness-kit 当前没有相应的人力、测试环境和内容维护范围。

3. **安装依赖外部工具**

   它依赖 `skills.sh`、MCP 服务和具体客户端。harness-kit 的价值之一是可以只用标准库直接运行，不能为了技能目录重新引入重依赖。

4. **上下文成本高**

   安装越多技能，客户端启动时需要加载的描述越多。对普通项目而言，这会挤占真正需要的项目上下文。

### 可以借鉴的最小部分

- 技能应有明确的触发条件和验收方式。
- 技能内容需要实际任务验证，不能只检查 Markdown 格式。
- 重要规则应记录“为什么”，避免后人反复推翻已解决的问题。

这些原则可以用于未来的技能说明，但不需要复制它的技能目录、安装器或发布流程。

## 项目二：superpowers

### 它是什么

一套面向编码 Agent 的开发方法论，由 15 个可组合技能和少量会话引导组成。它覆盖需求澄清、设计、计划、TDD、系统排错、代码评审、分支收尾和跨客户端分发。

### 做得好的地方

1. **工作流完整**

   它从“不要直接写代码”开始，依次处理需求、设计、计划、实施、评审和交付。每个阶段都有明确产物。

2. **完成前验证很硬**

   它要求 Agent 在声称完成前实际运行完整验证命令，并读取输出和退出码。局部测试通过不能代替完整测试套件。

3. **排错先找根因**

   它要求复现问题、读取错误、检查最近改动、收集证据、提出单一假设，再修复和验证。连续多次修复失败时，转而质疑架构。

4. **计划面向执行**

   计划不是泛泛的任务列表，而是包含具体文件、接口、测试、验证命令和可独立验收的步骤。

5. **技能是过程工具**

   技能不只是知识文档，而是约束 Agent 在特定阶段使用特定流程。这比单纯写“请认真工作”更可执行。

6. **跨客户端分发**

   同一套核心技能适配多种客户端，并用自动化测试检查部分插件和 hook 行为。这个方向值得学习，但不应立刻复制全部适配矩阵。

### 不适合 harness-kit 的地方

1. **强制触发过重**

   它要求只要认为有极小概率适用，就必须先调用技能，并加入大量反合理化话术。这会提高流程遵循率，也可能让简单任务被完整流程拖慢。

2. **完整方法论超出当前产品边界**

   worktree、子代理、逐任务评审、分支收尾和设计门禁是一套开发运行时。harness-kit 目前是文件与命令工具，不应突然承担全部编排职责。

3. **SessionStart hook 会重新引入机器配置**

   它通过 hook 自动注入引导内容。不同客户端的 hook 格式不同，失败时还可能静默或打断会话。harness-kit 刚移除此类机制，不应为了“自动生效”重新承担兼容维护。

4. **TDD 被设为绝对规则**

   TDD 对行为变更和 bug 修复很有价值，但不适用于所有配置、文档、探索性原型和资源改动。harness-kit 应要求可验证，而不是强制所有任务走同一种测试仪式。

5. **规则体量过大**

   长文档、多个流程技能和平台适配会增加上下文成本。我们刚把通用规则收敛进 `TASKS.md`，不应再次拆成大量并行规则。

### 可以借鉴的最小部分

1. **先看上下文，再问问题**

   已有项目先读相关代码、文档和状态，只询问现有材料无法回答且会改变实现的问题。

2. **排错先复现根因**

   问题先复现并收集证据，再提出单一假设；修复后验证原始症状和回归，而不是凭感觉连续试改。

3. **完成必须基于本次证据**

   完成声明必须对应本次实际运行过的检查。局部检查通过不等于全套通过，未运行的项目要明确列出。

4. **重要规则记录理由**

   规则本身写在 `TASKS.md`，为什么这样定可以记录在项目权威文档中，避免反复讨论已解决的问题。

## 与 harness-kit 的定位对照

| 维度 | harness-kit | superpowers | skills-skills |
|---|---|---|---|
| 核心目标 | 项目上下文、Agent 准则、任务恢复 | 完整编码工作流 | 领域技能目录 |
| 主要产物 | 可检查的项目文件与 CLI | 过程技能与客户端插件 | 大量可安装技能 |
| 是否自动注入 | 不自动 | 通过 hook / 客户端适配 | 由技能客户端发现 |
| 是否编排任务 | 不编排 | 强编排 | 不编排 |
| 维护重点 | 文件契约、状态一致性 | 技能行为与流程 | 内容、工具、模型与平台 |
| 适合直接复制 | 不适用 | 否 | 否 |

## 建议吸收到 harness-kit 的内容

### 现在吸收

只改 `TASKS.md` 的受管 Agent 工作准则，不新增文件类型、hook 或运行时。

建议把现有表述补强为：

- **先读再问**：已有项目先读取 `PROJECT.md`、`TASKS.md`、`STATE.json` 和相关代码；只问材料无法回答且会影响实现的问题。
- **排错顺序**：复现问题 → 读取证据 → 检查最近改动 → 提出单一假设 → 最小修复 → 验证原始症状和回归。
- **完成证据**：只根据本次实际运行的检查报告完成；局部通过不等于全套通过，未运行项必须明确说明。

这些内容与现有五组准则重合，应合并进同一份 `TASKS.md`，不另建 `DEBUGGING.md`、`VERIFICATION.md` 或新的技能包。

### 暂不吸收

- 强制技能调用。
- 自动 SessionStart 注入。
- 完整设计门禁和逐任务子代理流程。
- 强制所有任务使用 TDD。
- 技能市场、安装目录和 82 个领域技能。
- 多客户端插件矩阵。

### 以后按证据评估

- 当技能数量超过个位数时，再引入技能格式校验和行为测试。
- 当多个真实客户端都需要同一入口时，再做一份正文到多格式适配器。
- 当真实任务数据证明简单规则不足时，再考虑独立排错或验证技能。

## 风险判断

| 方案 | 风险 | 判断 |
|---|---|---|
| 原样复制 superpowers | 产品膨胀、上下文过长、流程拖慢简单任务 | 不做 |
| 复制 skills-skills 技能库 | 维护和验证成本超出当前能力 | 不做 |
| 引入自动 hook | 客户端兼容和机器残留风险 | 不做 |
| 只补强现有 Agent 工作准则 | 改动小，需要真实任务验证效果 | 推荐 |

## 实施状态

已实施的最小吸收：

- 在“先澄清，再执行”中补充“先检查已有材料，只问会改变实现的问题”。
- 在“按可验证目标执行”中补充根因排错顺序，以及原始症状与回归验证。
- 明确局部检查不等于全套检查，完成声明只依据本次实际运行的证据。

未引入强制技能调用、自动 SessionStart 注入、完整 TDD 门禁、子代理编排或多客户端插件矩阵。

## 下一步

1. 保持当前产品定位：Agent 工作准则、项目事实和当前任务恢复。
2. 用 3–5 个真实任务比较修改前后的行为，至少观察：
   - 是否减少无依据假设和无关改动。
   - 是否更早发现根因。
   - 是否减少没有验证证据的完成声明。
   - 是否让简单任务明显变慢。
3. 只有真实使用暴露缺口时，再考虑新增技能或自动适配。

当前 Agent 工作准则仍以 `TASKS.md` 为准。
